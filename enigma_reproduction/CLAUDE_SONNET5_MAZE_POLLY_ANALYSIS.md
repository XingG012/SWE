## maze：模拟器不符合真实迷宫规则

模型实际读到了反编译、汇编和成功判定，识别了自修改代码及 R15 计数。
第 18 步写出的 BFS 却只检查下一地址是否在 `0x400000..0x410000` 的大范围内，
没有检查该地址是否为有效节点、节点类型和已经修改成 RET 的状态。
`visited` 使用 `(addr, depth)`，允许在不同深度重复进入同一地址。
达到深度 64 就打印成功，也没有运行真实二进制或服务端验证候选。

因此第 19 步的 `Solution found` 只是模型自己写的模拟器的输出。
用其自身地址公式重放该 64 位候选，只覆盖 17 个不同地址；第 17 步就重复了
第 5 步的地址。这进一步说明脚本忽略了真实的节点和不可重复访问约束。
第 20 次主模型调用入账后上限超过预算，动作被框架替换为 `exit_cost`。
日志未出现候选得到真实程序或服务端认可的证据。

## polly：工具误用与代数建模错误

第 5–7 步把 `connect_exec` 当作可运行任意 Python 的接口，连续得到
`Unknown syntax`。实际连接工具是命令解释器，源码没有提供 Python eval。
后来模型改用 pwntools 脚本，正常取到了服务端数据，网络并未阻止解题。

题目公开源码定义 `K = GF(p_)`，加密和理想都在这个有限域的多项式环中。
模型第 14 步却定义 `PolynomialRing(ZZ)`，改变了代数域，导致错误的约化。
三个密文的常量扰动分别为 `-randI`、`+randI`、`+123`，相加后还剩 `+123`。
正确关系应在有限域中满足：

```
reduce(C1 + C2 + C3) = 999 * admin_code + 123 (mod p_)
```

模型直接提取常数并做 `constant // 999`：没有扣除 123，也没有做模意义下的逆运算。
字节转换失败后，它仍把大整数候选当成正确结果。
第 18 步真实服务器明确回复 `Wrong flag`，证明候选不正确。
随后下一次模型调用使费用上限超出阈值，没有继续修正。

还存在一个小的流程问题：题面写 `src/ideal.sage`，实际容器中附件平铺为
`ideal.sage`，使第一步 open 失败。第二步 ls、第三步 open 已恢复，因此不是
后续密码学错误的根因。一次 nc 命令被框架判超时，也增加了开销。

## 预算上限的含义

当前适配器不知道缓存写入 TTL，按配置的 1 小时写入单价 4 USD/M 估算上限，
按 5 分钟 2.5 USD/M 估算下限。预算检查使用上限。
两题上限减下限分别为 0.224148、0.20517 USD，恰好全部来自写入单价差，
这次空命中字段并未额外扩大范围：该次写入已覆盖整个输入。
所以“达到 0.8”是保守参考估算触发，不能当成中转站实际账单。
如果真实写入价格对应下限，两题在停止时的费用都还不到 0.8；日志没有给出
足够依据选择实际 TTL 或中转价格，不能自行认定应改为低价计费。

本轮主要失败来自模型策略和数学建模，保守费用上限限制了后续纠错机会。
没有证据表明密钥、模型分组或上一轮缓存兼容错误造成了这两次失败。
